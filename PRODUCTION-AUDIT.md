# Studio production readiness audit

Audited November 23, 2026 at `https://studio.kmoybox.com`.

**Private beta: NO-GO. Paid public launch: NO-GO.** The deployed confirmation and recovery callbacks redirect to localhost, the public legal and support routes checked are missing, and production account isolation, data persistence, and operational recovery still need direct verification. The payment endpoint is unavailable for test delivery. No production settings were changed and no payments were initiated.

## P0 · Before inviting external beta users

- **Fix confirmation and recovery URLs.** Automated live requests to `/auth/confirm` and `/auth/recovery` without tokens returned HTTP 307 with `Location` values of `http://localhost:3000/login?confirmation=failed` and `http://localhost:3000/forgot-password?expired=1`. The user’s iPhone screenshot independently shows the confirmation flow ending on localhost. The source falls back to localhost if `STUDIO_SITE_URL` is unset. The HTTP results cannot distinguish a missing variable from an explicitly wrong value. With approval, verify the value on the Vercel deployment serving the domain, set it to `https://studio.kmoybox.com`, and verify the Supabase Site URL, exact confirmation and recovery redirect allowlist, and email templates. After redeployment, use fresh email links and test the full lifecycle with synthetic mailboxes.
- **Verify live account isolation and persistence.** Public redirects establish session gating only. A controlled two-account test must confirm the deployed database has the current migrations and RLS policies, that each account sees only its own journal, goals, and workbook progress, and that answers and journal entries survive refresh, logout, and login. Test normal product interfaces and perform the policy tests in a matching isolated database.
- **Make journal save failures recoverable.** A prior local automated test verified a visible warning, retained text in the open editor, and successful retry. Unsent content is at risk if the tab closes or reloads after a failed save. Verify live failure feedback using a synthetic entry and an interrupted connection. Provide a clear unsaved indicator and navigation protection or a tested privacy-conscious draft recovery flow before beta.
- **Publish privacy, terms, and support information.** The live sign-in page did not expose those links. `/privacy`, `/privacy-policy`, `/terms`, and `/support` returned 404. Link the approved policies and an accessible support contact from signup and Account. Verify that a signed-in synthetic reviewer can find and complete account deletion. The live signed-out Account redirect does not prove deletion works.
- **Verify operational recovery.** Hosting logs, application error alerts, database backup schedules and retention, and a restore drill require authorized provider access. Confirm logs are available, alerts reach an owner, and a backup can be restored to an isolated project. Restrict access to logs and check that journal text and confirmation or recovery tokens are excluded.
- **Verify supported browsers with real devices.** Complete the authenticated core workflows on iPhone Safari, Android Chrome, and desktop browsers. The iPhone screenshot documents the current confirmation failure. The automated Chromium attempt stopped at a certificate trust error in the audit environment before rendering. HTTPS requests through the environment’s HTTP client succeeded. Neither observation establishes a general browser or production TLS failure.

## P1 · Before paid public launch

- **Verify Stripe test checkout and refund revocation.** The live webhook responded HTTP 503 to a single unsigned JSON POST. The repository handler returns 503 before signature validation when Stripe test configuration is unavailable, so the probe did not establish signature verification. Verify test-mode environment variables, the exact webhook URL, event subscriptions, signed delivery, and retries in approved test staging. Use a synthetic buyer to verify pending orders stay locked, paid orders unlock, duplicate delivery is harmless, and a successful full refund revokes access. The local tests and SQL authorization checks provide supporting evidence only. The current app rejects live Stripe credentials and live events by design. A paid public launch requires a separately approved live-mode implementation and rollout.

## P2 · After the blockers

- Add recurring synthetic smoke checks for callback destinations, protected-route redirects, and signed test webhook events. Expand real-device coverage and set a hosted performance baseline.
