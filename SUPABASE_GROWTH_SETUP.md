# Supabase setup for The Becoming Studio

The versioned migrations belong to KMOYBOX Workbook Studio. The growth feature uses the same Supabase Auth users and the same project as Workbook Studio. Apply the database changes before serving the application revision that reads the new columns.

## Schema and compatibility

| Domain | Relation | Storage and access |
| --- | --- | --- |
| Growth profiles | `growth_profiles` | Owner-scoped view of `profiles`. Auth provisions and deletes the profile. The owner can select a timezone here and change their display name through the existing Account flow. |
| Growth goals | `growth_goals` | Owner-scoped view of `goals`. Existing milestones and goal history keep their foreign keys and behavior. |
| Guided exercises | `wheel_of_life_entries`, `values_assessments`, `thought_records`, `emotion_entries`, `boundary_entries`, `identity_maps`, `cognitive_reframes`, `relationship_entries`, `body_awareness_entries`, `future_self_entries`, `inner_critic_entries`, `life_timeline_events` | Writable, invoker-security views of `growth_exercises`. Each filters its module and checks that writes remain in that module. The life timeline view stores each saved timeline as one guided exercise with its ordered prompt responses. The Social Integration guided exercise also uses `growth_exercises`. |
| Habits and check-ins | `habits`, `habit_logs`, `mood_checkins`, `weekly_reflections` | Owner-scoped views of the existing growth tables. Existing calendar and idempotency keys remain unique. Habit logs reference the same-owner habit and cascade on deletion. |
| Social activity | `social_goals`, `social_interactions` | A social goal links to an existing same-owner goal. A private interaction can link to a same-owner social goal. Removing the goal leaves the interaction available with its link cleared. |
| Notification preferences | `notification_preferences` | One row per owner. Daily and weekly reminder times are opt-in settings. Wheel of Life reminders appear on the dashboard once due. No delivery service or background scheduling is required. |

All private base tables in this feature have RLS. The named views run with invoker security and inherit the underlying table's grants and policies. Private activity records have UUID keys, timestamps, and same-owner relationships where applicable. Anon has no grants on these growth interfaces. App actions use the verified user's session and a publishable key. The service role has no grants on the growth exercise or tracking tables, new social and preference tables, or their growth views.

## Drafts, comparisons, and dates

- A member can save a partial current exercise. A complete exercise requires a response for each prompt. Wheel of Life ratings are integers from 1 to 10 stored as strings in the existing response format. A later substantive edit to a completed exercise copies the earlier completion into separate history. Compare a member's own completed rows with `completed_at is not null`, ordered by `completed_at` and `id`. The module page displays previous completions and the dashboard displays recent activity. The export includes all saved versions.
- The dashboard's Calendar settings allow selecting a named timezone. The previous Pacific setting is the default. Server Actions and database write checks use the selected zone. Check-ins retain the recorded local date and timezone when a member later changes settings. Weekly reflections use Monday as the start of the local week. Workbook Studio's existing calendar behavior is independent of this growth setting.
- The current exercise is identified by `is_current = true`. Use the UUID for an individual historical row. Data API clients that need upserts should target the existing base table and its natural conflict key for habits/check-ins/reflections. The app updates the current exercise using its saved revision to detect concurrent edits.
- Social interactions and reminder preferences are available as owner-scoped database interfaces. The existing Social Integration exercise continues to save its private guided responses through the normal exercise flow.

## Export, deletion, and privacy

- Account → Personal data exports and resets owner-scoped activity using the existing authenticated RPCs. The JSON retains its existing fields and adds `growthProfile`, `socialGoals`, `socialInteractions`, and `notificationPreferences`. Exercise history is included in `growthExercises`. Reset removes saved growth data and restores the default timezone, preserving account credentials and purchases. Full account deletion cascades from the Auth user.
- Keep private answers, notes, and contact reflections out of analytics, session replay, AI services, support tooling, and error notifications. Keep private pages, Server Actions, and export responses outside shared caches. Next.js Server Function argument logging is disabled in development. Application failures should record sanitized operation names or database codes only. Never capture request/response bodies, Supabase error details or hints, SQL bind values, or exported JSON in monitoring. Review database log settings so error details and parameters are omitted when possible. Verify redaction with synthetic input before enabling hosted monitoring.
- The migration adds no notification jobs, data-sharing policies, Realtime publication entries, or AI integrations. Keep existing dashboard roles separate from private response access. Restrict infrastructure access and backups to approved operators, and verify retention and restore policies for deleted data. Database owners and infrastructure operators retain their platform privileges.
- Keep any server-only Supabase administrative credential in the existing server environment. Never prefix it with `NEXT_PUBLIC_`, include it in client bundles, or print it in CI.

## Migration sequence

1. Confirm which Supabase project serves `studio.kmoybox.com` from the deployed environment configuration. Compare its migration ledger and schema with this repository. The earlier connected project inspection did not establish the production target. If the ledger differs, resolve the drift before applying either growth migration.
2. Start a disposable local Supabase stack with the repository-compatible CLI. Its documented baseline is v2.80.0. With an existing disposable local database, use `supabase migration up --local`. For a fresh local stack, use `supabase start`. Never use a reset command against a hosted database.
3. Run `npm run test:db`, `npm run typecheck`, `npm run build`, and `npm test`. Run `npm run test:auth` against the synthetic local Auth/Mailpit environment described in README. The growth SQL suite exercises timezone boundaries, preserved history, export/reset, ownership and parent-link checks, and denial for anonymous and overprivileged application callers.
4. Use an isolated staging project and confirm its identity before linking. On CLI v2.80.0, review the staging ledger with `supabase migration list --linked` and preview the pending SQL with `supabase db push --linked --dry-run`. Review the target object's state and the exact migration list. Apply only the reviewed migrations with `supabase db push --linked`. If using a newer CLI, check the current command help for hosted confirmation flags. Keep seed loading disabled for hosted rollout.
5. With two synthetic staging accounts, test calendar changes across a day boundary, saved drafts, completed history, same-owner links, account-to-account denial, export, reset, and account deletion. Verify the authenticated REST interface and ensure private text does not appear in the application's logs or monitoring events. Confirm workbook access and the existing account flows still work.
6. For an authorized production rollout, confirm backup and recovery readiness, apply the reviewed migrations to the verified target, then deploy the matching code. If remediation is needed, keep the migrated schema and use a forward fix or compatible app revision. Avoid serving the pre-history growth editor after new history exists because its reads assume one row per module. Preserve member-created history during rollback.

## Centralized notification delivery

Apply `20261124210618_centralized_reminders.sql` before deploying the notification settings and poll route. Delivery uses Supabase row-level security and the signed-in Studio session. It needs no additional environment variables, scheduler, mail transport, push service, or service-role key. The existing sign-in SMTP configuration remains separate.

The Personal Growth dashboard and modules check for notices on load and about once a minute while visible. Opening or returning to the Studio can deliver a notice missed earlier in its period. Nothing is sent while the Studio is closed or hidden. Browser delivery uses the page Notification API on a secure origin (or a supported localhost origin), requires permission for each browser and device, and can also be suppressed by operating-system settings. Some mobile browsers expose the API but do not support page-created notifications. In-app notices remain available wherever the Studio runs.

Saving centralized settings takes over delivery from the module-level reminder banners. Their existing schedules and source records are retained. Mood reminders still follow the active days and slots in Mood Tracker. A goal due reminder can catch up for seven days, and a dated boundary or future-self reflection can catch up for 30 days. A period uses the shared Studio timezone. Repeated local clock times reuse the same occurrence, and a skipped clock time becomes due after the jump. The durable ledger limits delivery to one record per type and occurrence and suppresses another occurrence of that type for 12 hours after a timezone change or delivery. Snoozing explicitly reopens browser delivery after the chosen elapsed interval. Browser claims across tabs are at most once per appearance. Failed system notification display does not retry automatically; members can still review notices in the inbox.

Do not configure public caching for the poll endpoint. The browser payload and system notification omit journal text, mood labels, habit names, goal titles, and other private record content.

## Personal Growth Content Manager

Apply `20261124212000_growth_content_manager.sql` before deploying the updated Studio. The Workbook Content Editor links to the Personal Growth Content Manager and uses the existing `workbook_editor_accounts` allowlist. Grant and revoke this role through trusted database administration. It gives access to both libraries of editorial content and does not change the owner-only policies on member records.

Editorial items have immutable revisions. Saving a draft cancels pending publication and leaves any current publication in place. Scheduled publications use UTC and take effect on the first request after the scheduled time. A later immediate publication or archive supersedes a previously scheduled revision. Archiving a module availability item restores the module's default availability. Editing availability does not remove members' saved records. Published editorial resources appear on the relevant module or dashboard. For the Workbook Studio Daily Reflection card, create a Reflection prompt with the Dashboard → Daily Reflection destination and put the prompt text in Content. The newest effective prompt appears on the card and in the journal opened from it. The built-in daily prompt is used when no editorial prompt is eligible. The application's built-in exercises and their historical field mappings remain versioned in source.

Engagement shows distinct signed-in module visits for the last completed UTC month, rounded to bands of ten with smaller cohorts suppressed. The deduplication ledger stores only an account reference, module, and month. Old visit rows are removed on subsequent visits after their reporting month, and account deletion removes that account's rows. Administrators receive only the aggregate function result. No scheduler, external analytics service, or elevated client key is needed.

For the signed-in Playwright coverage, use synthetic accounts in a local Supabase instance. Set `STUDIO_AUTH_TEST_EDITOR_EMAIL` and `STUDIO_AUTH_TEST_EDITOR_PASSWORD` for an account in the editor allowlist, and `STUDIO_AUTH_TEST_MEMBER_EMAIL` and `STUDIO_AUTH_TEST_MEMBER_PASSWORD` for an ordinary account. Run `npm run test:auth -- growth-content-manager`. The database coverage is in `supabase/tests/growth_content_manager.sql`.
